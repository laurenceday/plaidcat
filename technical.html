1 · The connect flow, actor by actor

The full production trace, sixteen steps, with what each actor does. B is the borrower, F the Wildcat frontend, S the Wildcat backend, P is Plaid, K the bank. Source: stream A, verified against the OpenAPI spec. official

#ActorWhat happens
1B → FClicks "Connect Operating Accounts."
2F → SAuthenticated request for a link token.
3S → P/link/token/create with products: ["transactions"], transactions.days_requested: 730, additional_consented_products for later products, a webhook URL, account filters for business checking and savings, and an internal borrower id. The 730 is a one-shot: it cannot be raised later without deleting and re-linking the Item.
4P → S → FReturns a link_token, valid four hours; the backend forwards it to the frontend.
5FOpens Plaid Link with it.
6B in LinkSees the consent pane: Wildcat's name, Plaid's role and privacy policy, and under Data Transparency Messaging the exact data types and use cases requested. Accepts, then picks the institution.
7B at KOAuth path (the US majors): redirected to the bank's own site or app, logs in there, picks which accounts to share on the bank's screen, approves. Credentials never touch Plaid. Legacy path (long tail): enters bank credentials inside Link, answers MFA there.
8B in LinkConfirms account selection unless the bank's picker already settled it. Link shows Connected.
9FonSuccess fires with a public_token and metadata. Sends the token to the backend. It expires in 30 minutes.
10S → P/item/public_token/exchange returns the access_token and item_id. Both are encrypted and stored server-side, never sent back to the browser.
11P → KPlaid begins pulling: the most recent 30 days first, then the historical backfill toward the 730-day request.
12S → PFirst /transactions/sync call with an empty cursor. This also arms the sync webhook; skipping it is a common integration bug.
13P → SSYNC_UPDATES_AVAILABLE webhook, first with initial_update_complete, later with historical_update_complete. The backend verifies the ES256 JWT on every delivery before trusting it.
14S → POn each webhook, loops /transactions/sync with the stored cursor until has_more is false. Upserts added and modified rows, tombstones removed ones, saves the cursor atomically. Data has landed.
15steady statePlaid re-polls the bank one to four times a day. Each change fires the webhook and step 14 repeats. Before a credit decision, an on-demand /transactions/refresh (paid add-on) forces a fresh pull.
16exceptionsITEM_LOGIN_REQUIRED or a pending-disconnect warning sends the borrower through update mode; same tokens continue afterward. Revocation webhooks halt use. Offboarding calls /item/remove (the docs-recommended call; the API spec also carries /item/products/terminate), which also stops billing.

2 · Items and access tokens

What an Item is

One authenticated connection to one institution login, created through Link. It groups one or more accounts and carries the product set, the user's consent scope, the webhook URL, health state, and billing. Linking the same credentials twice makes two independent Items, except where banks de-duplicate: Chase and PNC invalidate the older Item when the account sets differ, and Schwab allows only one active Item per user per app. official

What the access token is

The long-lived credential the backend pairs with Wildcat's client id and secret to read that Item. Plaid's docs say it plainly: "An access_token does not expire." It dies only by explicit removal, rotation, or revocation. A leaked token alone is useless without the API secret, but treat it as a bank-data credential: server side only, encrypted at rest, never in logs. official

3 · Consent, scoping, expiration

Consent is scoped on two axes, both fixed at link time. Products and data scopes come from the four product arrays on /link/token/create and surface to the borrower in the consent pane; accounts come from Account Select or the bank's own OAuth picker. Broadening either requires a fresh consent session. Products can never be removed from an Item, only the whole Item can go. official

  • The clever array. additional_consented_products banks consent now and bills nothing until the endpoint is first called. An underwriting flow that starts transactions-first can add Auth or Liabilities later without another Link session.
  • Consent visibility shipped ahead of regulation. /item/get exposes consented products, use cases and data scopes; /consent/events/get holds a three-year consent log. Wildcat gets an audit trail for free.
  • Expiration reality, August 2026. There is no universal US consent expiration. The often-repeated "90-day rule" is a UK/EU artifact (Europe runs about 180 days). Eleven US institutions require periodic OAuth consent refresh per Plaid's docs, every 12 months unless noted: American Express, Bank of America (new API only, with old-API Items force-disconnected mid-March through late October 2026), Brex (every 3 months), Capital One, Charles Schwab, Citibank, Fidelity, Navy Federal, PNC, TD Bank, and USAA (18 months). Plaid's machinery for a 12-month reauthorization regime is built and explicitly dormant, waiting on the 1033 rulemaking; a successful update-mode pass resets an Item's consent clock as though newly created. official

4 · Revocation from three sides

WhoHowEffectSignal to Wildcat
Wildcat /item/remove, the docs-recommended offboarding call; the API spec also carries a newer /item/products/terminate Access token and derived processor tokens die immediately; subscription billing ends. Existing Asset Reports survive. Deterministic, it made the call
Borrower via Plaid Portal (my.plaid.com) Revoke the app, revoke Plaid, or request deletion from Plaid's systems Access stops, billing ends. Data already delivered to Wildcat stays with Wildcat, subject to the contractual deletion duty on request. USER_PERMISSION_REVOKED webhook
Borrower at the bank The bank's own OAuth permission manager Item breaks. Unreliable: USER_ACCOUNT_REVOKED fires only for Chase, PNC and Truist; elsewhere nothing until the next pull fails with ITEM_LOGIN_REQUIRED
Asymmetry worth knowing

Neither side's off-switch cleans the other's UI. Removing an Item can leave a stale "active" entry in the bank's OAuth manager, and bank-side revocation may never ping Plaid. Wildcat's borrower offboarding runbook should tell borrowers to revoke at both my.plaid.com and their bank, and Wildcat should treat webhook silence as no proof of consent. official

5 · Webhooks

Webhooks are at-least-once "go fetch" signals, not payloads of record. Delivery retries for 24 hours with four-fold backoff from 30 seconds and a 10-second response timeout. Every delivery carries a Plaid-Verification header holding an ES256 JWT; verify it against /webhook_verification_key/get, check the token is under five minutes old, and compare the body hash before trusting anything. Deliveries come only from four published IPs (52.21.26.131, 52.21.47.157, 52.41.247.19, 52.88.82.239, subject to change). One more revocation nuance from the docs: bank-side consent revocation surfaces as ITEM_LOGIN_REQUIRED after roughly 24 to 48 hours, and a single-account revocation fires no webhook at all. official

Data webhooks (TRANSACTIONS)

SYNC_UPDATES_AVAILABLE is the one that matters: it fires on the initial pull, the historical backfill, and every scheduled update, and only after the first /transactions/sync call arms it. RECURRING_TRANSACTIONS_UPDATE covers recurring streams. INITIAL_UPDATE, HISTORICAL_UPDATE, DEFAULT_UPDATE and TRANSACTIONS_REMOVED are legacy, kept for back-compatibility.

Lifecycle webhooks (ITEM)

ERROR carries ITEM_LOGIN_REQUIRED. PENDING_DISCONNECT (US/CA) and PENDING_EXPIRATION (EU/UK) warn 7 days ahead. USER_PERMISSION_REVOKED and USER_ACCOUNT_REVOKED signal revocation. NEW_ACCOUNTS_AVAILABLE says the borrower opened an account worth adding. LOGIN_REPAIRED says the Item healed without Wildcat's help.

6 · Is the connection live?

Persistent, yes. Live, no. Plaid polls each institution on its own schedule, typically one to four times a day, and callers mostly read Plaid's cache. There is no real-time feed. On-demand freshness before a credit decision comes from /transactions/refresh, a paid, access-gated add-on that pulls synchronously in roughly ten to thirty seconds. Balance has the same split: /accounts/get is free and cached, /accounts/balance/get forces a real-time pull and bills per call. official

7 · Production requirements

  • Two environments: Sandbox and Production. The free tier is now the Trial plan, ten live Items, which replaced Limited Production for new US/CA teams on 15 April 2026. official
  • Full production: dashboard application, use-case review by Plaid's Customer Oversight team, billing setup, and about a week of processing. OAuth registration then runs per institution; Schwab can add six weeks, and both Chase and PNC gate on the security questionnaire (waived on Trial plans) official. The one-week processing figure is support-site lore; the docs carry no number operator-reported.
  • The questionnaire's contents are public: encryption at rest and in transit, access reviews, MFA, penetration tests, background checks, incident response official. Reading it as effectively SOC 2-shaped, such that a team without those controls will struggle, is this run's inference inferred.

8 · The brief's questions, answered

Can permissions be scoped?

Yes, at link time, on the product axis and the account axis. Broadening needs a new consent session. Narrowing means removing the Item.

Can access be revoked?

By all three parties: Wildcat by API call, the borrower through Plaid Portal or their bank, the bank by killing the OAuth grant. Revocation stops future access only; delivered data stays delivered.

How long does the credential survive?

Indefinitely by design. Nothing about the token needs refreshing. What decays is bank-side consent at specific institutions, and credentials when borrowers change passwords.

What happens on credential expiry?

The Item enters ITEM_LOGIN_REQUIRED, a webhook says so, and update mode fixes it with the same token and unbroken history. Warnings arrive 7 days early where the break is scheduled.

Can Wildcat terminate?

Yes, and it must for billing hygiene: errored Items keep billing until removed. /item/remove is the docs-recommended offboarding call; the API spec also carries /item/products/terminate.

Does the connection stay live?

It persists until someone kills it, refreshed one to four times a day, with a paid on-demand refresh for decision moments. Real-time it is not.
